## 第一部分：开场白（约 1 分钟）

各位老师好，我的课题是 **FitPro 健身管理系统**，一个面向健身房的数字化管理平台。

传统健身房普遍存在几个问题：会员管理靠纸质记录、课程预约靠微信群接龙、训练数据全靠脑子记。所以我的目标就是开发一套系统，让健身房的管理者和会员都能用上数字化工具。

目前项目已经完成了 **前四个阶段**的开发，进入了第五个收尾阶段。下面我从四个方面汇报：**项目概述、技术架构、已完成功能、当前进展与计划**。

FitPro 系统解决的是 **两个角色** 的需求：

**第一，管理端** —— 健身房的管理人员和教练。他们需要一个后台来管理会员、教练、课程、排课，还要能看数据统计。

**第二，会员端** —— 来健身的普通用户。他们需要能约课、看训练计划、记录训练数据、签到打卡。

系统的核心业务逻辑围绕三条线展开：
- **一条是课程线**：从创建课程 → 安排课表 → 会员预约 → 到场签到
- **一条是训练线**：从制定训练计划 → 按日执行 → 记录每组数据 → 查看进度
- **一条是会籍线**：从购买会员卡 → 签到扣次 → 续费延期

这三条线覆盖了健身房运营的主要场景。

## 第三部分：技术架构（约 2 分钟）

【翻到技术架构页】

技术上采用 **前后端分离架构**：

**后端**使用 Java 17 + Spring Boot 3.2，搭配 MyBatis-Plus 操作数据库。认证这块用了 Spring Security 和 JWT 双 Token 机制——什么意思呢？就是用户登录后发两个令牌，一个短的 2 小时过期用来正常访问，一个长的 7 天过期用来续签，这样既安全体验又好。

数据层用了 MySQL 8.0 做持久化存储，Redis 缓存做令牌管理。一共有 **19 张数据库表**，覆盖了用户、课程、训练、会籍、签到等全部业务。

**前端**使用 Vue 3.4 + Vite 5 + Element Plus 组件库。状态管理用的 Pinia，HTTP 请求用的 Axios。页面交互上做了毛玻璃效果、动效卡片、响应式布局等视觉优化。

前后端通过 RESTful API 通信，接口文档用的是 Knife4j（Swagger 的增强版），可以在线测试接口。

## 第四部分：功能演示（约 4-5 分钟，核心部分）

### 4.1 登录注册

系统支持三种角色：**超级管理员、教练、会员**。注册时选择角色，登录后自动跳转到对应的操作界面。

【演示一下登录：用 admin/admin123 登录管理端】

### 4.2 管理端功能

登录后进入管理后台，左侧是导航菜单：

**① 仪表盘**
进来第一眼看到的是仪表盘。这里有6张数据卡片——**会员总数、今日签到数、课程数量、教练人数、待开课程**。下面是图表，展示近七天的签到趋势和注册趋势。最下面是待办排课列表和最新的签到记录。

【鼠标在仪表盘上扫一下】

**② 会员管理**
这个页面可以搜索、筛选会员，查看每个人的详细信息。在详情页里可以看到会员的会籍情况——比如他买了什么卡、还剩多少天、签到记录。还可以直接在这里操作 **办卡、续费、冻结、退卡**。

【点开一个会员，展示详情】

**③ 教练管理**
教练列表，可以新增教练、启用或禁用账号。

**④ 课程管理**
管理端可以 **创建课程、编辑、上下架**。创建完课程后，在排课管理里给课程安排具体的时间、地点、带课教练。

**⑤ 运动库管理**
这里维护所有的训练动作，按部位分类——胸部、背部、腿部等等，每个动作有详细的图文说明。

**⑥ 系统管理**
包括：发布公告（可以置顶）、查看操作日志（谁在什么时间做了什么操作，系统自动记录）、系统配置。

【快速过一遍，不用点开每个页面】

### 4.3 会员端功能

【切换到会员端，演示】

会员端的界面更偏移动端风格，底部有四个导航：

**① 首页**
展示个人运动概览和快捷入口。

**② 课程**
在这里浏览所有课程，按类型筛选。点击课程可以看到排课时间表，有位置的课程可以直接预约。预约成功后可以在"我的预约"里查看或取消。

【演示一次预约流程】

**③ 训练计划**
教练给会员制定训练计划后，会员在这里按周查看。每天的训练内容——做什么动作、做几组、每组多少次。训练时打开记录模式，填写实际完成的重量和次数。

**④ 个人中心**
包含个人资料编辑、修改密码、身体数据录入（体重体脂等）【这一块以后会做成图表展示趋势】、会籍信息卡片（显示卡类型、到期日、剩余次数）、签到打卡（每天点击签到，按月统计）。

### Q1: 你这个系统跟市面上已有的健身房管理系统比有什么优势？

**答：** 主要优势有两点。第一，我们采用了**前后端分离架构**，界面更现代，交互体验更好。第二，系统集成了**课程预约、训练记录、会籍管理**三大核心业务于一体，而市面上很多系统只做其中一块。

### Q2: 如何保证课程预约不会超卖（两个人约到同一个名额）？

**答：** 我们用了**乐观锁**机制。预约时不是先查再改，而是用一条 SQL 原子操作：`UPDATE course_schedule SET current_count = current_count + 1 WHERE id = ? AND current_count < max_capacity`。这样数据库层面就保证了不会超卖。

### Q3: 你的数据库为什么不做外键？

**答：** 这是出于性能考虑。外键约束会影响写入性能，而且在分布式场景下外键没有意义。我们的做法是**在代码层面保证数据一致性**，ER 图中保留关系，数据库不建物理外键。

### Q4: 权限控制是怎么做的？

**答：** 采用 Spring Security + JWT 的方案。用户登录后拿到 Token，每次请求通过过滤器解析 Token 中的角色信息，然后用 `@PreAuthorize` 注解在接口级别做权限校验。前端也通过路由守卫做了角色拦截，双重保障。

### Q5: 系统目前完成度如何？哪些是还没做的？

**答：** 核心功能都已完成，现在处于**第五阶段收尾**。还没做的包括：单元测试、Docker 部署。计划中的但没有实现的增强功能有：短信通知、定时任务自动处理到期会籍、头像上传。

### Q6: 你在项目中负责了哪些部分？（如果你的老师说这不是你一个人能做的量）

**答：** 这个项目确实有一定复杂度。我的做法是**先搭骨架再填内容**——先把前后端框架、数据库、通用组件搞好，然后一个模块一个模块地推进。本质上这是一个典型的单体应用，大部分代码是模板式的 CRUD，有框架支撑后开发效率比较高。

### Q7: 你这个项目跟你的课程相关吗？属于什么类型的课题？

**答：** 这是一个**Web 全栈开发**类型的课题。从选题上说，它属于**管理信息系统**方向，综合运用了 Java 后端、Vue 前端、数据库设计等课程知识。

### Q8 (杀手问题): 你觉得这个系统还有什么不足？

**答：** 如果坦诚说，时间有限，还有几个方面可以做得更好：
1. **测试覆盖**：目前主要是手动测试，缺少自动化单元测试
2. **部署**：还没有容器化部署方案
3. **高并发**：像秒杀预约这种场景，虽然用了乐观锁，但没做压力测试
4. **监控告警**：没有接入日志监控系统

> 这个问题如实回答反而加分，说明你有思考深度。
